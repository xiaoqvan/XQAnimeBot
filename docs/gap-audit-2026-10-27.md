## 1. 集合层面：Rust 缺 5 张表

newdbtest 的 `database/initDb.ts` 建 13 张表，Rust 只用了 8 张：

```
anime  episodes_meta  torrents  cacheItem  config  bangumi_users  pendingReviews  task_checkpoints   ← Rust 有
resources  cache_resources  cacheAnime  ai_calls  img_cache                                        ← Rust 全无
```

关键是 `resources` / `cache_resources`——**这两张就是 `btdata` 的替代品**。TS 把「某部番第几集、
由哪个字幕组发的、消息在哪、videoid 是什么」写进 `resources`（`EpisodeResourceDoc`：
`anime_id / episode / episodeId / groups[] / title / message / messages[] / videoid / unique_id /`
`cache_id / source / createdAt`），`cache_resources` 是审核中的同款。导航正文、内联取视频、
集数纠正都从这两张表读。Rust 里 `"resources"` 唯一的命中是 ultralight 渲染器的静态资源目录。

连带：`navVideoMessage` 语义也错了。newdbtest 里它是**导航分页消息**（`page` = 第几页，指向
导航频道的文本消息），集数资源不在其中；Rust 的 [push_episode](crates/fuyubot-plugin-anime/src/nav.rs)
却把每集视频消息连同 TS 没有的 `episode` 字段写进去，两边互相污染。

## 2. 两个文档形状对不上

### 2.1 `bangumi_users` —— 硬不兼容，且是硬失败

TS 是 camelCase：`accessToken` / `refreshToken` / `expiresIn` / `tokenType` / `bgmUserId` /
`scope` / `authTime`；`id` 是**内部自增序列**，Bangumi 用户 id 放 `bgmUserId`。

Rust 的 [BangumiUserDoc](crates/anime-core/src/models.rs#L388-L405) 是 `access_token`
（**snake_case，没有 rename**），`id` 存 Bangumi 用户 id，还**必填** `username` / `nickname`。

实测：newdbtest 真实形状反序列化 → `missing field 'username'`；即使补上 `username`，
`accessToken` 也进不到 `access_token`（有 `#[serde(default)]`，静默变空串）。

后果：接老库时 `/collect` 和收藏回调一律报「请先 /bindbangumi 绑定」；Rust 写的绑定 TS 也读不到。

### 2.2 `pendingReviews` —— 主键和载荷都不一样

| | TS | Rust 现状 |
| --- | --- | --- |
| 主键 | 自增 `id`（`getNextSequence("pendingReviewId")`） | 字符串 `key`（`rss:<cleanTitle>`） |
| 载荷 | `item` / `anime` / `episodeId` / `episodeSort` / `sentMessages[]` / `primaryMessage{}` / `matchDetail` / `episodeMatch` | 一个 `payload` blob |
| 回调数据 | `Y_anime?r=<id>` / `F_anime?r=<id>` | `review:approve:<key>` |

[store.rs:423](crates/anime-core/src/store.rs#L423) 注释写「宿主接口没有自增 id」——不是宿主没有，
是当初照 `main` 抄的。两边不能互换。

### 2.3 自增序列

TS 的 `getNextSequence(name)` 是 `config` 集合 `{type, seq}` 配 `$inc`，三个序列
`cacheItemId` / `bangumi_user_id` / `pendingReviewId` 共用。Rust 的 `cache_item_add`
用 `max(id)+1`（[store.rs:221](crates/anime-core/src/store.rs#L221) 注明单写者等价）——
功能够用，但不推进 `config` 里的序列文档，两边交替写会撞号。

## 3. P0：业务主链断掉的地方

**新番只打一行日志。** [poll.rs:331-334](crates/fuyubot-plugin-anime/src/poll.rs#L331-L334)
`SeasonDecision::New` 只做 `new_anime += 1`。newdbtest 的 `handleNewAnime` 走两条路：

- **置信度 ≥ 0.9（先发后审）**：建档 → 匹配章节 → 下载 → 发导航消息 → 发视频到正式频道 →
  `saveAnimeResource` → 再次更新导航 → `createPendingReview` → 带候选列表的审核提示。
- **< 0.9（回退）**：`animeinfo` 搜索 → `buildAndSaveAnimeFromInfo(cache=true)` → 下载 →
  发**缓冲频道** → `saveAnimeResource(cache=true)` → 提示确认。

**缓冲频道完全不存在。** `sendMegToCache` 发到 `ADMIN_GROUP_ID` 的 `ANIME_GROUP_THREAD_ID`
话题，标题用 `item.title`，发完置 `等待纠正`。「命中但集数没对齐」这条最常走的路，
Rust 现在只是 `log!(Info, "命中但集数没对齐")`（[poll.rs:310-317](crates/fuyubot-plugin-anime/src/poll.rs#L310-L317)），
视频没发出去，也没有纠正入口。

**审核提示 1 个 vs 4 个。** newdbtest 有 `promptAdminProvideAnimeInfo` /
`promptAdminConfirmAnime` / `promptAdminConfirmAnimeEpisodes` /
`promptAdminConfirmAnimeWithCandidates`。Rust 只有
[review.rs](crates/fuyubot-plugin-anime/src/review.rs) 一个 154 行通用提示。

**回调 2 种 vs 6 种。** TS 分发 `Y_anime` / `F_anime` / `N_anime` / `N_ep` / `colorep` / `chgcol`。
Rust 只有 `review:approve|reject` 和 `collection:<id>:<kind>`。其中 `N_anime` / `N_ep`
是**多轮交互**——改提示语后用 `client.iterUpdates()` 等管理员 reply，解析章节 id 或 bgm
链接再继续（[hasAnime.ts:394](d:/GitHub/_ts-newdbtest/CallbackQuery/hasAnime.ts)、`:560`）。
Rust 没有「等下一条回复」的状态机。

## 4. P1：行为不等价

### 4.1 LLM 匹配是两套东西

newdbtest 的 [bangumiAgent.ts 1102 行](d:/GitHub/_ts-newdbtest/bangumi/bangumiAgent.ts)：OpenAI
Responses API + **工具调用**（`searchAnimeCandidates` / `getRelatedSubjects` / `getEpisodeDetail`，
[tools.ts](d:/GitHub/_ts-newdbtest/bangumi/tools.ts)），`MAX_ITERATIONS=8` 迭代循环，输出带
`confidence` / `reason`。Rust 的 [ai.rs 213 行](crates/anime-core/src/ai.rs) 只有两次单发
chat/completions + JSON 解析，无工具调用、无候选搜索、无关联条目、无置信度。
`database/ai.ts` 还会把每次调用写进 `ai_calls`，Rust 无任何记录。

**顺序也反了**：`matcher.ts` 是 AI 优先，Rust 是规则优先、AI 兜底
（[poll.rs:286-303](crates/fuyubot-plugin-anime/src/poll.rs#L286-L303)，注释里承认是刻意偏差）。

### 4.2 没有并发管理器和真正的任务控制

newdbtest 的 [AnimeProcessorManager.ts 481 行](d:/GitHub/_ts-newdbtest/anime/AnimeProcessorManager.ts)：
普通 worker 3 + **MKV 独立队列 1** + 重型转换独占槽 1 + `progressMap`（阶段/百分比/标签）+
`cancelActiveByIndex` / `cancelActiveByTitle` / `cancelAllActive`。Rust 是
[chain.rs](crates/fuyubot-plugin-anime/src/chain.rs) 里 `const WORKERS: usize = 3` 的 cvar 计数；
`/canceltask` 直接回「暂不支持单独取消」（[bot.rs:559](crates/fuyubot-plugin-anime/src/bot.rs#L559)）；
`/progress` 只打 4 个计数器，而 TS 的 `progress.ts` 有 210 行、含 21 种 qB 状态中文对照表。

**MKV 预检路由也没有**：`checkTorrentFormat` 在下载前借 qB 的 metadata 通道（paused 态加入、
轮询 `has_metadata` 最多 60 秒）判断容器，纯 MKV 进独立队列。Rust 是下完再挑最大视频文件。

### 4.3 导航消息只做了一半

newdbtest 的 `sendMegToNavAnime` 约 350 行：拉 `getSubjectById` + `getEpisodeInfo` → 并行持久化
评分/简介/集数 → `generateBangumiNavImage`（带 `fansubs`）→ 拿 hash 比 `navImageHash` →
图变走 `editMessageMedia`（并把 `file_id` 写进 `img_cache`）、只文本变走 `editMessageCaption`
（先用 `getMessageLinkInfo` 取旧值比较以避风控）→ 资源分页作为回复消息逐条发出并写
`navVideoMessage`，每步 `sleep(5000)`。Rust 的
[nav.rs 253 行](crates/fuyubot-plugin-anime/src/nav.rs) 只有：发一次卡、caption 一行、`edit_message_caption`。

`navmegtext`（[text.ts](d:/GitHub/_ts-newdbtest/anime/text.ts)：1024/4096 双限测量、summary
300→100 逐级压缩、`compareEpisode` 排序、`[第N页](link)` 页码导航）和 `AnimeText`
（原名/中文名/发布组/发布时间/追踪标签 + 导航·收藏·标记看过·吐槽箱四链接）在 Rust 里
只有一句 `名字｜第 N 集`（[chain.rs:725](crates/fuyubot-plugin-anime/src/chain.rs#L725)）。

### 4.4 视频发送字段不全

`sendMegToAnime`：`updateTorrentStatus("上传中")` → `extractVideoMetadata` 出封面和真实
`width/height/duration` → 分段走 `sendMessageAlbum` → `has_spoiler = anime.r18` →
`timeout: 1800` → **失败重试一次** → 置「完成」，`finally` 清理。Rust 的
`duration/width/height` 写死 0、`has_spoiler` 写死 false
（[td.rs:123](crates/fuyubot-plugin-anime/src/td.rs#L123)、`:167`）、无封面、无相册、
无重试、沿用 simplify 默认 30 秒超时。封面抽取需 ffmpeg 插件新增 thumbnail 方法
（现有只有 `ping`/`capabilities`/`probe`/`plan`/`transcode`/`extract_subtitle`/`split`/`job_*`/`prune`）。

### 4.5 种子状态只走两态

`TorrentStatus` 定义 8 态，代码只写 `Downloading`（chain.rs:220）和 `Done`（chain.rs:356）。
TS 在 `等待下载 → 等待元数据 → 下载中 → 下载完成 → 上传中 → 完成 / 等待纠正 / 失败`
上都有调用。另外 Rust 有 `has_torrent_by_magnet` 但插件里一次没调用，TS 是标题+磁力两道去重。

### 4.6 标签没有过滤

`extractFilteredTagNames`（[utils/index.ts:123](d:/GitHub/_ts-newdbtest/utils/index.ts)）剔除
`^\d{4}年`、纯数字、`tagExcludeList`。Rust 的 `to_anime` 原样搬运，`tagExcludeList` 0 命中。

## 5. 命令集与权限

newdbtest 注册 15 条，每条带 `scope` + `permission`：
`start / web / bindbangumi / exitbangumi / searchanime / s / setanimer18 / ConAnimeInfo(jz) /`
`addanime / addnewanime / updateanime / progress / canceltask / animeblacklist / testbgimg`。

- **缺**：`start`（深链）、`ConAnimeInfo`/`jz`、`addnewanime`。
- **`addanime` 语义完全不同**：TS 是 `/addanime <章节ID> <磁力URL>`（拉 torrent 详情 → 解析 →
  下载 → `saveAnimeResource` → 更新导航 → `editMessageCaption` 补全文案）；Rust 的
  `/addanime <条目id>` 只是拉 Bangumi 条目建档（[bot.rs:213](crates/fuyubot-plugin-anime/src/bot.rs#L213) 注释自认）。
- **多出来**：`about / bgm / collect / help / ping / selftest / status`，TS 没有——属 Rust 自带基础设施。
- `/animeblacklist` Rust 只能列（[bot.rs:522](crates/fuyubot-plugin-anime/src/bot.rs#L522)），TS 能增删。

**权限**：TS 是 `isUserAdmin(ADMIN_GROUP_ID, sender)`（真调 `getChatMember`）+ `config` 的
`super_admin`。Rust 只有 `owner_id` 等值白名单（[bot.rs:153-176](crates/fuyubot-plugin-anime/src/bot.rs#L153-L176)），
且 `owner_id == 0` 时**完全不校验**。

## 6. Bangumi 接口与 OAuth

- 缺 `getEpisodeById`（`GET /v0/episodes/{id}`）——`/addanime`、`/addnewanime`、`/jz`、
  `N_anime`、`nullEp` 全依赖它。
- 缺 `searchAnimeCandidates` / `getRelatedSubjects` / `getEpisodeDetail`。
- 无 `retryRequest`（[bangumi/get.ts:13](d:/GitHub/_ts-newdbtest/bangumi/get.ts)，3 次重试 / 10 秒）。
- 搜索体缺 `nsfw`（TS 是 `{keyword, sort:"rank", filter:{type:[2], nsfw:true}, limit:10}`）。

**OAuth 只有 `refresh_token`，且从没被调用**（[oauth.rs](crates/anime-core/src/bangumi/oauth.rs) 全仓仅定义）。
TS 有完整四步 `getAuthUrl` / `getAccessToken` / `refreshAccessToken` / `getTokenStatus`
（[bangumi/callback.ts](d:/GitHub/_ts-newdbtest/bangumi/callback.ts)），外加 `getBgmToken`
按 `authTime + expiresIn` 提前一分钟自动刷新。Rust 的 `/bindbangumi` 是让用户粘一个 token，
只存 `access_token`——**七天过期后没有补救路径**。

## 7. Inline 模式（上一版也说反了）

上一版说「TS 也没有 inline」——那也是 `main` 的结论。newdbtest 的
[index.ts](d:/GitHub/_ts-newdbtest/index.ts) 注册了两个 `inlineHandlers`：

[inline/episodeVideo.ts](d:/GitHub/_ts-newdbtest/inline/episodeVideo.ts)）。

**但这条做不了**：宿主 `fuyubot-abi` / `fuyubot-core` 里 `inline` 是 0 命中，ABI 只有
`UPDATE_EVENT` / `RESPONSE_EVENT` 和 `on(...)`，没有 inline 注册入口；
`fuyubot-tdlib-ext` 的 `answer_inline_query` 只能发、收不到查询。
这是**宿主侧限制**，得先在 FuyuBot 加 inline 事件分发。

## 9. 不建议现在动的部分

- **web 端**：按你的要求排除。（事实：newdbtest 的 `web/routes` 有 8 个文件 26 个端点，
  除读之外还能下发 `addanime`/`addnewanime` 任务；Rust 的
  [web.rs](crates/fuyubot-plugin-anime/src/web.rs) 是 5 个只读 GET。）
- **`img_cache`：先不动。** TS 里 `updateImgCache` 从 `@db/update.ts` 导入，但该函数在
  newdbtest 里**没有导出**（全仓 0 命中），`img_cache` 只在注释出现两次——TS 自己还没写完。
- **`processTree` / `processWatchdog`**：TS 管子进程树用的，Rust 的 ffmpeg 在独立插件里，不需要。
- **字幕组解析表**：Rust 是**超集**（规则 34 vs TS 31，别名 8 vs 5，多出 `Kirara Fantasia` /
  `LoliHouse` / `雪飄工作室(FLsnow)`），不用补。
